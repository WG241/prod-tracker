# Historical roster capture

## Summary

Capture each closed person/week once, with real evidence and a System audit. Track full roster completion separately, and keep uncertain history unavailable rather than inventing it.

## Model and migration

Add WorkWeek.rosterCapturedAt DateTime? @db.Timestamptz(3) and TrackerSettings.trackingStartsOn DateTime? @db.Date. Preserve all existing columns, relations and timestamps. The new fields initially contain null. trackingStartsOn must be a four digit year Monday, and a nonnull rosterCapturedAt must be at or after freezesAt.

Use one additive transactional, idempotent SQL migration, with guarded columns, named constraints and triggers. Once trackingStartsOn is nonnull it cannot change or become null, and its settings row cannot be deleted. Once rosterCapturedAt is nonnull it cannot change or become null. WorkWeek startsOn/planningLocksAt/freezesAt are immutable after creation, and a frozen WorkWeek cannot be deleted. Manual lock and unlock fields retain their existing purpose. These additions do not weaken the existing frozen roster trigger or permit a snapshot repair. Install the source projection guards below in the same migration. Use the established security invoker function conventions, fixed search_path and restricted direct execute privileges. Regenerate Prisma and verify the migration twice without rewriting historical timestamps or captures.

Before first initialization, ensure the current WAT WorkWeek in a separate committed coverage unit. In the initialization transaction, lock the singleton settings row, verify the required source guards are enabled and that the same current Monday already exists as a committed week. If Monday changed between those units, retry the prerequisite rather than initialize against an unprotected week. Then initialize trackingStartsOn to that Monday, with one System audit `HISTORY_TRACKING_STARTED`. The audit targets TrackerSettings/workforce-group and stores version 1, trackingStartsOn and historicalProtectionVersion 1. Explicitly set its createdAt from fresh clock_timestamp() after waits; a transaction start default is insufficient. The preexisting committed current week ensures the source guards already apply if initialization spans its freeze. Commit the baseline value and audit together. Repeated startup, seed and CLI retry preserve both. Missing, duplicate or contradictory initialization evidence is PROTECTION_UNAVAILABLE, not permission to invent a past audit. If the settings row or schedule is invalid, report unavailable capture and keep ordinary serving alive.

## Coverage and roster

Process all existing WorkWeek rows that have frozen. Ensure missing weeks from trackingStartsOn through the current Monday, using the validated persisted settings and the existing calendar helpers. The current week may be ensured before it freezes. Existing older weeks are retained; absent weeks before trackingStartsOn are not created. If a missing old week's cutoffs cannot be supported by the available settings history, leave that gap unavailable for repair rather than assert a historical schedule. In particular, a settings.updatedAt later than the missing week's freeze is not proof of that week's old planning cutoff. Existing persisted cutoffs remain authoritative.

Roster membership is every person whose dated assignment overlaps [WAT Monday 00:00, freezesAt), including all five roles and zero task/inactive/full leave cases. Existing trackers outside otherwise reconstructable membership are diagnostic candidates, never silently discarded or rewritten. Exclude the unassigned foundation health identity.

For a person/week, use referenceForWeek and assignmentForWeek with a reference of freezesAt minus one millisecond. Reject overlapping assignment intervals, missing required role relationships or an inconsistent owner/assignment link. If no assignment is active at reference, the final assignment overlapping the week supplies attribution, as in spec 0002. Existing activeAt and expectedWorkingDays define account eligibility and the Monday through Friday workday/leave union result. Nonemployee and nonexpected cases receive zero days, not omission from the roster.

The snapshot is version 1 with userId, displayName, role, accountStatus, businessId/businessName, unitId/unitName, managerId/managerName and departmentLabel, with the existing role dependent nullability. Its assignmentId is the chosen historical assignment, expectedWorkingDaysSnapshot is 0..5, and snapshotAt is actual successful capture time, not a backdated freeze timestamp. Capture does not require an auth identity or provisioned login; roster eligibility is a domain fact.

## Reconstruction safety

Use one pure validator and eligibility result for the worker, diagnostics and History availability. A valid existing captured snapshot is authoritative: preserve its fields and timestamp, regardless of later changes to current people or labels. Do not compare it to today's mutable labels or recompute its expected days.

For an uncaptured person or an unstamped whole roster, require freezesAt at or after the immutable protection start audit time and enabled source guards. Earlier uncaptured periods are HISTORICAL_FACTS_UNAVAILABLE even if current rows look plausible. Existing individual frozen snapshots remain readable in those periods. They alone do not prove that a whole old roster contains every original member, so they cannot automatically establish a legacy roster completion marker.

For a new capture, require coherent dated assignment and leave inputs and enough evidence for the mutable account and label fields. The conservative automatic rule is that relevant User, Business, Unit and referenced manager User updatedAt values must be no later than freezesAt. Their creation times and role relationships must also be consistent with the selected historical assignment. A mutable open tracker updated after freeze is likewise insufficient evidence. If those checks fail, return HISTORICAL_FACTS_UNAVAILABLE; current values or an old mutable tracker alone cannot prove which intervening changes occurred. This intentionally permits false negatives instead of silently asserting a false historical account state or name.

Existing explicit dated deactivation, leave cancellation and return fields retain their meanings under the current calendar helpers. Do not infer a missing activation timeline, name history or settings version. Invalid intervals, labels or required relationships yield fixed diagnostic reason codes. An existing captured row with invalid structure or contradictory immutable relationships yields INVALID_SNAPSHOT and is never overwritten, deleted or made valid by moving its timestamp.

### Historical source guards

Protect historical contributions at the database boundary, not only through promised future writer behavior. A protected frozen window is an existing WorkWeek whose freezesAt is at or before clock_timestamp(), or an absent week within persisted trackingStartsOn coverage whose normal Saturday WAT freeze has passed. Prefer a stored week's actual cutoffs over its normal implied window. These guards also protect an incomplete roster and a temporarily absent covered week.

For EmploymentAssignment INSERT/UPDATE/DELETE, reject any change to historical membership, attribution or eligibility in such a window. Compare the old/new clipped assignment interval within [WAT Monday 00:00, freezesAt), plus userId, role, businessId, unitId, managerId and departmentLabel. An insert or delete with a nonempty historical intersection changes that projection and is rejected. A later ordinary closing of an open assignment is allowed when its clipped historical intersection and attributes are identical for every protected week. Thus closing it now does not prevent an ordinary role change, while moving its old boundary into a frozen week does.

For LeaveRecord INSERT/UPDATE/DELETE, preserve the historical Monday through Friday coverage vector used by expectedWorkingDays at each protected week's freeze reference. Compute it from startsOn, actualReturnOn or expectedReturnOn, and cancellation effective at that reference. Reject any change to that historical contribution, including a backdated insert or deletion. userId is immutable. Once actualReturnOn is nonnull it cannot be rewritten or cleared; once cancellation is recorded its cancelledAt/cancelledById cannot be rewritten or cleared. A new later return/cancellation or future extension is allowed only when historical coverage remains identical. These append rules make later effective events reconstructable without pretending an unrecorded old field version exists.

The source BEFORE guards themselves acquire the old/new owner User rows for update in stable id order and applicable stored WorkWeek rows for share before taking the final fresh clock_timestamp() and checking projections. Do not rely on a later foreign key check to acquire owner serialization: otherwise a prefreeze insert could wait until after a captured snapshot commits. Reevaluate which windows have frozen after those waits. Ordinary writers should take the same owner locks before issuing source UPDATE statements; direct SQL gets the same safety from the trigger, with possible deadlock errors requiring a complete retry. The automatic completion fence below blocks assignment mutations while the roster is revalidated. Missing covered windows are protected through the immutable coverage baseline, so delaying WorkWeek creation is not a bypass. Test the guards through direct SQL as well as ordinary writer composition. Privileged reviewed repairs are separate operations; no application override switch or custom session flag bypasses these guards.

### Seed and test compatibility

On an empty database, seed historical assignments and leave sources before creating the historical WorkWeek rows. This is trusted initial fixture construction, not a runtime guard override. Repeated seeds must avoid issuing source INSERTs for existing stable ids: read/filter them under appropriate source table locks inside the atomic seed transaction. Do not add an unlocked primary key existence exemption to a BEFORE guard, because the conflicting row could be deleted concurrently. Any actual conflict UPDATE still receives normal source validation. New historical fixture additions to an already protected ordinary database require their own reviewed operation.

Historical setup fixtures in tests may use an explicitly isolated TEST_DATABASE_URL setup helper that suspends only these new source guards inside a transaction holding ACCESS EXCLUSIVE locks on the affected tables, inserts the arranged history, and restores the guards before commit. Other sessions cannot observe a disabled guard. Never suspend audit or frozen roster immutability, never expose this helper through server/CLI runtime imports, and never suspend protection while exercising behavior assertions. Existing tests that simulate HR changes by rewriting a historical assignment must instead close the current interval and create a new dated assignment, preserving their original access assertions. Constraint probes should use unrelated valid source dates so they still reach the constraint they intend to test.

Only a separately reviewed repair may establish missing facts or correct corrupt evidence. This feature's CLI does not accept a snapshot JSON payload, override switch, fake asOf or caller supplied expected days. New ordinary HR/account/settings writers must settle overdue affected captures before modifying facts that would otherwise become ambiguous, and preserve closed assignment history.

## Transactions and completion

Use short Read Committed transactions and the existing person before week lock contract. A person capture locks its User for update, dated assignments and leave rows for share, referenced label records for share in stable id order, the WorkWeek for share, then its WeeklyTracker for update. Obtain clock_timestamp() after waits, reread source facts, require that the week is frozen and apply reconstruction checks. Use that same database clock source for the final snapshot/audit capture timestamp. This aligns capture with the SQL source guards; ordinary read API clocks retain their existing source. A new assignment/leave insert is blocked by the owner User foreign key lock. Current/future HR writers must follow the same order.

If a valid captured tracker already exists, return unchanged without a new audit. Otherwise create or update only the uncaptured owned tracker with its historical assignment, context, expected days and actual snapshotAt, and insert one actorId null System audit `TRACKER_SNAPSHOT_CAPTURED` targeting that WeeklyTracker. Its safe payload contains week start, assignment id, expected days, reference time and capture time. A tracker or audit failure must not leave a partially updated capture unit. Do not rewrite unrelated history or emitted business events.

Person units are intentionally independent commits so valid history can progress while another entry is unavailable. After those commits, a separate short transaction first takes a SHARE table lock on EmploymentAssignment with a 500 millisecond lock timeout, then locks WorkWeek for update. Recompute required roster membership after both locks, validate every required snapshot, and check for inconsistent existing roster entries. This short fence blocks assignment inserts, updates and deletes while permitting the row SHARE reads used by person capture. Set rosterCapturedAt from clock_timestamp() immediately before the successful update and create one System `WEEK_ROSTER_CAPTURED` audit only if all checks and historical protection evidence pass. Store only safe count/time fields in that audit. Empty required rosters can complete with count zero. A partial, unproven or corrupt roster cannot complete.

Completion does not rely on a previous unlocked count. Concurrent person captures hold the shared week lock, so completion sees their committed results after waiting. The historical source guards reject retrospectively effective membership changes after completion commits as well. A lock timeout defers completion without a marker or audit. Preserve captured roster evidence and completion timestamps on every retry. Do not lock User rows or recompute captured eligibility in this completion transaction; it validates committed snapshots.

Initialize coverage and create missing weeks in short separate transactions, using settings/week locks and natural keys. Handle duplicate creation and deadlock races with at most three complete attempts. Retry fresh clocks and checks, never reuse a prewait permission result. Hold no transaction across a timer, telemetry write, UI interaction or another HTTP call. Pool and transaction bounds remain compatible with the existing five connection pool.

## Scheduler and operations

Start a nonblocking pass when the app starts and schedule a check every 60 seconds while it is running. Keep an in process single pass guard; cross process correctness comes from database locks and unique keys. Run one database unit at a time. The 20 second wall time admission budget applies to coverage, person capture and completion together; an admitted unit may finish within its existing 5 second max wait/15 second transaction timeout. Completion's table lock has the tighter 500 millisecond wait above.

Use keyset discovery and independent advancing cursors for the three phases. Each pass admits at most 10 missing week creation units, 50 person units and 5 whole week completion units. Round robin the phases and rotate the starting phase on each tick; advance each cursor after every attempted unit, including a refused or failed one. Back off failed targets until a later tick. No discovery loop may scan or create all missing weeks before allowing person/completion work. This prevents slow completion and old repair gaps from starving other work. Persisted snapshots, weeks, baseline and markers are durable progress; cursors may remain in memory. Large catch-up is eventual, with honest pending availability.

A normal person capture failure rolls back that unit, records a sanitized diagnostic and continues to unrelated candidates. A database or settings outage stops that pass and retries on a later tick. Do not prevent the HTTP app from serving existing valid history or other journeys. On shutdown stop scheduling and starting units, await the current unit within the existing shutdown deadline, then close the pool. Process death releases locks and rolls back an unfinished unit; committed snapshots remain reusable.

Provide `npm run history:capture -- [--week YYYY-MM-DD] [--user-id ID] [--apply]`. It uses the existing private operator database target guard and normal server database configuration, never an HTTP route. Default mode is diagnostics only, including when trackingStartsOn is null. --apply performs the same safe initialization/capture/retry path as the scheduler. A user selector requires a week selector; selectors cannot create a precoverage missing week or capture an unfrozen week.

Each invocation performs one bounded pass, not an unlimited drain. With --week --user-id, diagnostics and capture are restricted to that person/week, no other person or week is captured and no global completion marker is written. An absent selected WorkWeek may be safely ensured only if it is within coverage and reconstructable. The only permitted out of selector prerequisite writes are once only coverage initialization, its audit and ensuring the current WorkWeek in the preceding committed unit. A selected person returns success if its snapshot is valid/captured even when the global roster is incomplete. With --week alone, process only that week's people and completion; success requires a complete roster marker. With no selector, use all three bounded phases, and return remaining work rather than looping. Concurrent independent app ticks retain their own normal scope.

Return safe identifiers, candidate/captured/pending/repair counts and fixed reason codes. Never print connection strings, credentials, emails, names, full snapshots or raw database errors. Exit 0 for a complete requested result, 2 for remaining pending/repair work, and 1 for invalid arguments or infrastructure failure. Already captured retries create no audit and do not change timestamps. Ambiguous or invalid snapshots remain unavailable without an override.

Report person counts and week counts separately so an incomplete whole roster is not confused with a failed selected person. Fixed codes are CAPTURE_PENDING, CAPTURED, ALREADY_CAPTURED, ROSTER_COMPLETE, HISTORICAL_FACTS_UNAVAILABLE, PROTECTION_UNAVAILABLE, MISSING_HISTORICAL_SCHEDULE, INVALID_SNAPSHOT, INVALID_ASSIGNMENT, INVALID_LEAVE, INVALID_SOURCE, SETTINGS_UNAVAILABLE, NOT_FROZEN, NOT_FOUND, OUTSIDE_COVERAGE, RETRY_LATER and SERVICE_UNAVAILABLE. Capture/runtime infrastructure failures use exit 1; an unavailable historical fact or bounded remaining work uses exit 2. Public History maps validated snapshots to AVAILABLE, eligible uncaptured targets to PENDING, and unsafe/corrupt targets to REPAIR_REQUIRED without exposing private diagnostic records.

No new runtime environment variable or secret is required. Reuse existing database configuration and telemetry switches. Add a closed server diagnostic HISTORY_CAPTURE_FAILED with source background and location key history-capture through the existing sanitizer; public browser ingestion must not be able to claim this trusted source. Business audit is transactional; diagnostics are best effort after rollback or commit and never decide capture success. No task_submitted/task_approved event is emitted by capture.

## Critical checks

* Seed an entire roster with no tasks, inactive/nonexpected and full leave people, midweek role/manager changes and all five roles. Verify membership, one assignment attribution, exact WAT boundaries and 0..5 expected days. AC-4, AC-5.
* Initialize coverage once, skip absent weeks before baseline, create later zero submission weeks, respect existing cutoffs, and catch up after process downtime. AC-4.
* Freeze near a held owner/week lock, change a source before releasing it, and verify fresh facts after waiting. Race two workers and the private retry command without duplicate captures or audits. AC-5, AC-7.
* Race whole week completion with assignment inserts, interval changes and deletions. Verify the table fence and reject a backdated change after completion. Allow a safe later closing of an open assignment. Prove leave return, cancellation and extension guards preserve past workday coverage. AC-5 through AC-7.
* Preserve existing frozen labels/days after rename, reassignment, deactivation and leave changes. Refuse unsafe uncaptured rows when relevant mutable sources changed after freeze, invalid assignments and corrupt snapshots. AC-5, AC-6.
* Inject failure during tracker update, System audit and whole week completion. Assert complete rollback of that unit, unchanged old timestamps and continued valid unrelated progress. Never stamp a partial roster complete. AC-6, AC-7.
* Kill/restart a bounded pass, exercise cursor fairness, outage retry and shutdown, and verify diagnostics cannot override or rewrite evidence. AC-7, AC-10.
* Exercise all three phase budgets with large coverage gaps and permanent repair targets. Verify scoped CLI effects/exit codes, preprotection uncertainty, and long task date ranges in History availability counts. AC-2, AC-4, AC-6, AC-7.
* Apply the migration twice on separate test and actual Neon targets, verify guards and historic timestamp preservation, then run existing Employee and authentication regressions. AC-10.
